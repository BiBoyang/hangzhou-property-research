## 一、背景：PageIndex 是什么

开源项目 VectifyAI/PageIndex（GitHub 30K+ stars，MIT 协议）提出的"无向量 RAG"路线：

- **彻底抛弃 embedding + chunking**，改为两阶段：
  1. **树状索引构建**：从 PDF 版面/TOC 解析出层级树，用轻量 LLM 给每个节点生成摘要，存成 JSON 树
  2. **LLM 推理检索**：查询时把树结构（不含正文）塞给 Agent，LLM 像人翻目录一样逐层选节点，系统再按 node_id 加载对应页面内容，多跳导航（工具调用循环）
- **关键数据（需甄别口径）**：
  - FinanceBench 98.7% 准确率是 **Mafin 2.5（商业版产品，基于 PageIndex）**的成绩，覆盖全部 10,231 题；传统向量 RAG 约 30–50%。开源版本身没有这个数字
  - 开源版只有「prompt 驱动的树搜索」；**MCTS + 价值函数只在云端版**
  - 开源版**无 OCR**（只 PyPDF2/PyMuPDF 文本抽取），扫描件不可用
  - 查询延迟 30–120 秒（多次 LLM 调用），索引成本约 $0.001/页
- **核心洞察**：相似性（similarity）≠ 相关度（relevance）。向量检索是"语义氛围匹配"，对"同比恶化了哪些风险因素"这类需要理解意图+逻辑跳转的问题天然弱；LLM 基于结构化摘要推理选路，才接近人类专家查文档的方式
- **已知短板**：① 单文档树设计，跨文档语料库检索弱 ② 强依赖文档有清晰层级结构（扁平内容退化）③ 慢且贵 ④ 摘要质量决定检索质量（"还是 vibe 检索，只是换了个近似源"——Hacker News 主流批评）

## 二、场景适配分析结论（本次会话推导）

**财报（10-K/年报）**：PageIndex 绝对主场。结构规范、目录完整、交叉引用多、可审计性刚需，全部命中。

**券商研报**：分情况。
- 50 页+ 深度/行业报告：结构清晰，推理导航价值大 → 适合
- 10–50 页点评报告：结构尚可的可用；扁平的直接全文塞长上下文模型更划算
- 10 页内快评/晨报：不值得，直接塞
- 图表密集研报：开源版读不到表格里的数，需 OCR 预处理，核心卖点（精确数字）反而失效

**本项目（杭州买房决策支持）**：多文档对比为主（"各机构对上海房价底部判断""高盛 vs 瑞银观点异同""瑞银态度半年变化"），恰好是向量检索强项、PageIndex 弱项。**结论：不建议整体切换。**

## 三、本项目现状核实（2026-09-30 实际探查）

以下为本次会话直接读代码核实的事实，Codex 不必重复探查：

**检索层（`scripts/lib_search.py`）已是高配版混合检索**：
- FTS5（jieba 分词）+ sqlite-vec（Qwen3-Embedding-0.6B），RRF 融合（k=60）
- SYNONYMS 中英同义词扩展（瑞银→UBS、去化→inventory、杭州→Hangzhou 等）对冲中英跨语检索
- doc_boost 文档级先验：标题命中城市/机构 + 报告期与问题年月相符的文档整体提权（本质上是"人工规则版的 PageIndex 思路"）
- disclosure 噪声过滤（NOISE 列表）
- build_index 嵌入文本 = `title | heading | text`，标题承载强信号

**结构化指标层（本项目真正的差异化资产）**：中指院/克而瑞渠道文件 + metrics 表 + market_phase 规则引擎（市场阶段判断、来源分线、冲突保留、缺失期不填 0）。买房决策里精确数字（均价/去化周期/库存）靠这层，比任何 RAG 都可靠。

**其他**：docling 解析（保留 heading 层级 → 现成的树结构素材）、FastAPI 端口 8666、NDJSON 流式问答、4 个只读 overview API、eval 25 题。

**基线状态**：SESSION-2026-09-16 记录 25 题回归 25/25；rerank 探针（bge-reranker-base）已否决——中文中心 reranker 压英文 chunk 分且不理解机构/日期约束，与 doc_boost 设计冲突。

## 四、给本项目的建议（本次会话结论）

三级方案，推荐停在 Level 2：

- **Level 1（跑 eval 拿基线）**：已基本完成（25/25），不必重做。但可以补做**逐题归因分类**（见下）
- **Level 2（性价比最高的增强）**：加"深度精读"模式——混合检索粗筛出 2–3 份报告后，对单份报告用 PageIndex 式推理导航精读。**已有 80% 基础**：docling heading 层级在、chunks 表有 heading 字段可拼树、lib_llm 封装在。缺的只是：`build_doc_tree(doc_id)`（按 heading 拼 JSON 树 + 节点摘要）和 `reasoning_retrieve(query, doc_id)`（树塞 LLM 选节点 + 工具循环加载正文）+ 前端入口
- **Level 3（全量 PageIndex）**：不建议。61 份报告重建树索引 + 改写检索 + 改前端，成本高且收益场景占比低

## 五、留给 Codex 继续的问题（按优先级）

1. **25 题逐题归因**：把 eval 题按「精确数字类 / 跨机构对比类 / 观点演化类 / 单文档逻辑链类 / 未覆盖类」分类，量化"单文档深度理解"类占比——这是 Level 2 增量的理论上限。目前 25 题里明显属于"PageIndex 强项"的只有 1–2 题（如"大摩 Inflection 指的是什么"），需要确认值不值得做
2. **Level 2 具体设计**（如果决定做）：
   - 树的粒度：直接用 docling heading 层级，还是 heading + chunk 合并（研报 heading 少、单节可能超长，可能需要类似 PageIndex 的 span>10 页递归拆分逻辑）
   - 节点摘要：离线批量生成（入 ingest 管线）还是查询时惰性生成
   - 与现有 ask 管线的关系：独立端点（`/api/deep_read`）还是作为 ask 的自动 fallback（检索置信度低时触发）
   - 成本估算：61 份 × 节点数 × 摘要 token，vs 现有 1632 chunks 的 embedding 成本
3. **长上下文 baseline 对照**：本项目报告多为 10–50 页，先量化"整篇塞 Qwen/DeepSeek 长上下文"的准确率与成本，作为深度精读模式的对照组——如果全文直塞已经够准，Level 2 价值归零
4. **eval 扩充**：若决定做 Level 2，需先在 questions.yaml 补 8–10 道"单报告内逻辑链/观点论证"类题（如"高盛 260409 报告推荐一线城市布局的完整论证链是什么"），否则无法证明增量
5. **市场阶段判断的 LLM 化边界**：market_phase 是纯规则引擎（正确选择，可审计），PageIndex 思路若渗入这层需谨慎——规则可解释性是这层的核心价值，不要为推理而推理

## 六、一句话结论

现有混合检索 + 结构化指标层已覆盖买房决策 80%+ 需求；PageIndex 的价值不在整体替换，而在给"单份深度报告的逻辑链精读"补一个可选入口——且动手前必须先用「归因分类 + 长上下文对照实验」证明这 1–2 题场景的增量真实存在。
